A continuing experiment in teaching

Can a tutor
learn to teach?

We started by training a small model. Each test then exposed something the previous one missed: useful questions, follow-through, adaptation and what a tutor remembers. This is the record of those changes.

Follow the experiment ↓

An experiment note from Dio

First, learn what
good teaching looks like.

I wanted to find out whether an affordable model could learn the specific interactions that make Keating useful, and whether feedback could improve its next version.

Before training, I spent time on the harness: prompts, tools, the interface, learner submissions and manual review of whole conversations. Teaching is broad. I needed to discover what a good interaction looked like before turning it into a training target.

That work made the target concrete: ask a useful question, wait, build a valid activity, and grade what the learner actually submitted. My hypothesis is that a capable, affordable base model can specialize in this workflow. This run tests an early part of that hypothesis.

What is Keating?

An AI tutor built around the learner doing the thinking. It asks for explanations, alternative approaches and justified reasoning, then invites application to a real-world situation.

Its OpenUI activities stream into the conversation: questions, simulations, flashcards, quizzes and exams. Learner actions return structured evidence to the tutor. The interface is part of the lesson.

Was there enough SDPO?

Four SDPO updates across two feedback families make a pipeline pilot, not enough evidence for a reliable teaching improvement. More useful training would include diverse tool and OpenUI interactions, grounded feedback, and untouched evaluation families; simply increasing the update count is not a guarantee.

The earlier comparison above includes all seven predeclared scenarios across the untuned model, SFT, and SFT + SDPO. Each received the same Keating prompt, 16 tool schemas, scripted learner inputs, temperature 0, seed 42, and a 2,048-token output limit. Quiz and flashcard guidance changed after the checkpoints were trained. Native tool requests end a trace without execution. Preview controls are isolated report demonstrations, not live model turns.

The first identity run missed all six identity checks. The second continued from those weights with a higher learning rate, smaller batches and repeated short-context identity examples. It made 48 updates, using 36 training examples and 12 held-out examples.

The later SDPO-inspired continuation made four updates using two case-study feedback families. Checkpoint save, reload, sampling and the Keating proxy path succeeded. Three paired probes showed identity retention and a changed example, but do not establish improved teaching. This small pilot is not a reproduction of the full Trajectory SDPO study.

Tool schemas were available during SDPO; tools were not executed inside that training loop. Human retention and independent transfer have not been measured.

What these six SDPO updates actually did

Each update used a fresh response and its own compiler or contract feedback. All six training responses failed activity creation at temperature 1; none reached a grading turn. Failures stayed in the training evidence. The earlier proposed twenty-update repeat over historical feedback was never launched.

The unchanged evaluation uses temperature 0 and seed 42. It checks five activity families plus identity and arithmetic controls. The exam receives 4,096 output tokens; local serving allows 2,048, so this test does not prove exam serving. Both new checkpoints also returned valid four-card OpenUI activities through Keating’s SDK at the app’s temperature of 0.1, followed by a review in isolated memory.

The question-grading repair is promising, but one small development set is not a reliable estimate of generalization. This SDPO-inspired implementation is not a full reproduction of Trajectory’s SDPO++. Browser persistence, real learner recall and transfer remain unverified.

Questions from
the discussion.

Why this was worth trying, and what the results can actually answer.

Why work on the harness instead of just using a stronger model?

A capable base model is still necessary. The harness makes the desired behavior precise and observable: which UI is valid, when to wait, what counts as a submission, and whether grading executed. Manual review then asks whether that interaction was useful teaching.

We found conflicting identity and quiz-tool instructions after the run. Those were application problems worth fixing before blaming the weights. We did not compare the updated harness on a stronger model or on untuned Inkling, so this experiment cannot settle that tradeoff.

What is SDPO, and why only one rollout per situation?

Self-Distillation Policy Optimization uses the model itself, given extra feedback, to teach the version that did not see that feedback. The original SDPO paper studies this richer learning signal.

Trajectory’s Scaling SDPO investigates one trajectory per task, retained failures and stale rollouts. Its objective does not require ranking siblings in a group. Group size 1 is therefore a meaningful setting, not a broken group-relative update.

Our continuation used six fresh situations, one response per situation, with feedback from that response’s compiler or contract check. All six failed creation. It used PPO clipping and advantage clipping, but no stale rollouts: this was SDPO-inspired, not a reproduction of the full SDPO++ study.

Would DPO or KTO be better on a tiny budget?

Possibly. DPO learns from preferred/rejected response pairs without sampling during the optimization step. KTO can learn from desirable/undesirable labels without paired preferences. Both are relevant baselines, and neither was tested here.

The reason to try SDPO was to exercise learning from feedback tied to an actual response, not to claim the cheapest route to the highest score. For compute efficiency, first establishing a strong SFT and offline baseline is sensible. Continual learning can also use periodic offline updates; it is not exclusive to an online optimizer.

Are long conversation traces good training data?

They can preserve the context that a short answer loses: an earlier misconception, a pending question, a submitted activity and its real result IDs. That does not make every recorded assistant response a good target. Failed answers need appropriate feedback or repair; accepted answers still need review.

Our OpenUI SFT used eight authored long conversations, with four other conversations held out by topic family. System, learner and tool-result tokens were masked; assistant replies and calls were targets. The Downloads archive was audited, but source-derived synthetic continuations were not trained. Brief chat turns also do not imply a short model input: the prompt, tools and history still occupy context.

Is this already a continually learning tutor?

It is a pilot of the pieces: collect evidence, update an account-associated checkpoint, evaluate it and serve the saved adapter. SDPO was applied to Inkling-Small itself. The teacher used the same checkpoint with privileged feedback, not a different model.

The updates were manually launched and evaluated. This was not an always-on production loop, and compiler feedback was not evidence of human learning. Delayed learner outcomes, regression checks and a reliable promotion decision still need to govern any ongoing updates.

Did the results scale, or establish better sample efficiency?

We did not run a scaling curve, multiple seeds, a saturation study or a compute-matched DPO/KTO comparison. The full development checks moved from 2/7 to 5/7 after OpenUI SFT, then to 6/7 after SDPO. Two of those seven are identity and arithmetic controls. The additional passing case was a grading-tool repair; exams still failed.

Trajectory reports useful results in its tested settings and also notes limits in reaching behaviors the base model rarely samples. That motivates an experiment; it does not prove broad, pretraining-like gains here. Sample efficiency and compute efficiency are different questions, and neither comparative advantage was measured in this pilot.

Can we call this a state-of-the-art tutor for under $10?

No. Specializing an affordable model is the ambition. This run demonstrated parts of Keating’s interaction workflow, not superiority over other tutors or improved learner retention and transfer.

The earlier pilot’s local token-reservation scenarios estimate $6.63–$8.30 with the 50% discount already applied and different cache assumptions. That is an estimate, not a reconciled invoice; storage is additional. At that snapshot the safety reservation was $89.04, a separate padded control against the $100 cap. Later benchmark sampling is reported separately in the following chapters. “Under $10 estimated token cost” describes the earlier pilot.

The prompt changed after these results.

We aligned the Keating Bot identity, removed legacy quiz/deck schemas, clarified when to explain directly and made plan depth flexible. The recorded chats in this report use the earlier prompt, including its contradictions. Neither the trained nor untuned model has been re-evaluated with this later revision.

    Conclusion · What we learned
    We can change the model.
    Can we improve the lesson?
    This experiment made the training pipeline work and made the teaching problem clearer. It also exposed a gap: a model can learn the right identity, produce the expected format and pass a check while becoming a worse partner for a learner.
    
      
    
        
    What to take from this run
    What training changedWhat the benchmark revealedWhy the harness mattersHow to read the resultsThe next experimentWhat success would mean
    
        
    
          
    Specialization is possible. The target matters.
    The original bet was practical: start with an affordable model capable enough to teach, then specialize it for Keating’s conversations and tools. Saving an adapter, reloading it and serving it through Keating worked. The early training changed identity and response format; later development checks improved on some OpenUI and tool-repair cases.
    But manual use exposed something those checks missed. The SFT checkpoint felt less willing to ask useful questions and harder to learn with than the base model. That is an important user observation, even though we did not run a controlled study establishing its cause. Repeated short examples and exact-answer targets are plausible contributors; this run does not isolate which training choice caused the regression.
    The next target should reward a sensible teaching move in context. Several answers can be good: a brief explanation, a diagnostic question, a worked example or a challenge. Exactness belongs in tool schemas and grounded facts. It is a poor default for the wording of a lesson.
    What this says about SFT and SDPO
    It does not show that SFT is inherently harmful, or that SDPO would avoid the same failure. Our SDPO work was a small pilot, with limited feedback families. We did not measure scaling, establish superior sample efficiency, or complete a compute-matched comparison with DPO or KTO. Those remain experiments to run.
    Revisit the training record ↑
    
          
    Each revision changed what could fail.
    The first benchmark made basic contracts inspectable, but an 8/8 result showed how little those checks could say about teaching. The harder static cases broadened the task; they still could not show whether a tutor would execute its tools, recover from mistakes and carry a lesson forward.
    Moving into the real harness exposed that behavior. Version 3.1 replaced teaching instructions disguised as learner messages with ordinary questions and later feedback. Version 3.2 added relevant background, prior learning and profiles built through interaction. There was no separate live v3.1 cohort: its cases were carried into the v3.2 run.
    The resulting failures go beyond cost overruns. Gemma corrected a correct fraction answer. Qwen 3.8 graded answers nobody had submitted. Inkling claimed a memory write succeeded after it was rejected. These are concrete failures in the teaching relationship: inventing a misconception, inventing evidence or claiming continuity that does not exist.
    Inspect the recorded failures ↑
    
          
    The harness is part of the teacher.
    A model’s intention and the application’s state can disagree. One Inkling write was rejected because its quoted evidence changed an apostrophe. That needs a different remedy from inventing learner praise or ignoring a tool error. Training every failure as if it were a reasoning problem would hide defects in the surrounding software.
    The profile walkthrough makes a more useful target visible: retain a preference with its evidence, keep inference distinguishable from what the learner said, replace an outdated note when corrected, and use the revised note in a fresh session. Kimi’s notation trace demonstrates that replacement. It also contains other mistakes, so successful memory handling should not turn into a claim of flawless teaching.
    This supports spending time on the harness before another training run. It gives us observable actions and consequences to learn from. It does not remove the need for a capable base model, and it does not establish that harness work always produces the largest gain.

    A useful development instrument, with limits.
    The final cohort contains eight models across 23 cases: 184 attempted episodes, 183 completed harness runs and one call-limit failure. Of those completed runs, 29 contain an output-limit stop and are excluded from semantic aggregates. The remaining 154 have AI reviews. Finishing a run therefore means something different from producing a complete, useful lesson.
    These results help locate failures and compare the recorded configurations. They do not justify a definitive ranking of teaching ability. Reasoning controls differ, score coverage is uneven, reviewers are unblinded and uncalibrated, and the learner replies are authored. A fixed next reply can fit one valid teaching route better than another.
    Cost and speed are still useful when read with that context. A cheap response that requires several repairs may be an expensive lesson. A short response may be efficient or unhelpful. The charts separate these measurements; the conversations explain what the numbers alone cannot.
    What remains outside the evidence
    The current suite does not submit answers through generated quizzes, flashcards or exams. It does not test a harness evolving itself over long trajectories. Public cases are useful development targets, but repeated tuning against them makes fresh held-out cases necessary. Native cache usage is unmeasured, so the uncached cost view is a tariff scenario, not an invoice. None of these scores measures human learning, retention or transfer.
    
          
    What the next experiment should change.
    Start again from the base checkpoint and keep the current artifacts as a record. The following work is proposed, not a claim that new training has already run.
    1. Repair and freeze the harness. Make memory evidence validation robust without accepting fabricated quotes. Ensure failed writes remain visible to the tutor. Carry real learner submissions through OpenUI tools, and preserve the distinction between a generated activity, an answer and a grade.
    2. Turn trajectories into decision points. Use the existing traces to identify an earlier tutor response, the learner’s subsequent reaction and the relevant tool results. Separate learners and related topic families before generating training examples. Keep future feedback out of the student’s input and keep private source conversations out of this public report.
    3. Compare methods from the same starting point. Run an SDPO-only arm, with a small behavior-focused SFT baseline and DPO or KTO arms where the data supports meaningful preferences or judgments. Count feedback generation, labeling, retries and evaluation in the budget. A later learner reply can supply teacher-only context; it is not automatically a correct label or a reliable explanation of what went wrong.
    4. Require improvement without losing the lesson. Compare fresh cases under documented, controlled inference settings. Check whether the tutor asks when useful, explains when needed, connects supported prior learning, repairs errors and respects corrections. Retain the base model as a control. Promote a checkpoint only when the gain survives transcript review and does not trade away those behaviors.
    
          
    The outcome we ultimately care about.
    Keating’s aim is a learner who can do more after the conversation. The generative-learning ambition is to work near the edge of their understanding: invite them to consider alternatives, justify their reasoning and apply an idea in a real situation. Sometimes that requires a question. Sometimes it requires a clear answer before the learner can take the next step.
    To test that promise, we need people learning with the system, an assessment of what they could do beforehand, and later checks of unaided recall and transfer to a new problem. The benchmark can help us decide which tutor is ready for that study. It cannot substitute for the study.
    
        
    
      
    
      
    The most useful result of this run is a more precise next question.
    Can a tutor learn from a learner’s correction,
    carry it forward, and teach the next lesson better?
    We now have traces and a harness that make parts of that question testable. The next checkpoint has to demonstrate the improvement.
